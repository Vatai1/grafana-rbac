# Аудит безопасности форка (шаг 7)

Проверено всё, что форк добавляет или меняет в контроле доступа: права на источники данных, кастомные роли и их API,
выбор ролей в UI, YAML-загрузка ролей, включённые фичи лицензии (`dspermissions.enforcement`, `accesscontrol`).
Автоматическая проверка: `deploy/e2e/security_e2e.sh` (53 сценария, на PostgreSQL), плюс `ds_e2e.sh` и `roles_e2e.sh`.

## Найдено и исправлено

| # | Проблема | Риск | Исправление |
|---|---|---|---|
| 1 | Выдача прав на источник другой организации отвечала 500 вместо 404 (доступ не выдавался) | Низкий: шум в логах, раскрытие внутренней ошибки | Типизированная ошибка `errutil.NotFound` в валидаторе (`ossaccesscontrol/datasource.go`) |
| 2 | `POST /api/access-control/users/roles/search` принимал любое число `userIds`, по запросу на каждого | Средний: нагрузка на БД одним запросом | Ограничение 1000 id (`maxSearchUsers`) |
| 3 | Роль, выданная команде, отзывалась у участников с задержкой до 60 с | Средний: окно после отзыва доступа | Сброс кэша прав команды при любых изменениях её ролей; YAML-reload сбрасывает весь кэш прав |

## Проверено, проблем нет

**Доступ к источнику данных без права Query** — все пути закрыты (403/404): `/api/datasources/uid|name|:id`,
`.../health`, `.../resources/*`, `/api/datasources/proxy/*`, `/api/ds/query` (в т. ч. с expressions),
k8s API `*.datasource.grafana.app` (get/health/query/resource), `query.grafana.app`. Источник исчезает и из списков.

**Повышение прав через роли** — роль нельзя создать, изменить, назначить пользователю или команде, если в ней есть право,
которого нет у самого администратора: scope `*`, серверные действия (`users:create`, `orgs:create`, `global.users:*`),
`provisioning:reload`. `?delegatable=true` скрывает такие роли из выбора. Editor/Viewer не имеют доступа к API ролей
и не могут выдать себе права на источник.

**Изоляция организаций** — роли, источники, пользователи и команды другой организации недоступны (404);
`targetOrgId` разрешён только Grafana Admin; смена заголовка организации не даёт прав, которых там нет.

**Служебные роли** — managed- и fixed-роли Grafana нельзя изменить, удалить или назначить через API кастомных ролей
(всё ограничено префиксом `custom:` и организацией); имя из YAML всегда получает префикс `custom:`.

**Ввод** — имя роли, uid, scope и id проверяются (400); SQL собирается только из констант, значения — параметры.
Анонимные запросы — 401. Удаление пользователя из организации снимает его кастомные роли в ней.

## Остаточные риски (поведение Grafana / Enterprise, принято)

1. **Задержки кэшей Grafana.** Доступ к папкам и дашбордам проверяет authz-сервис с кэшем `GF_AUTHORIZATION_CACHE_TTL`
   (30 с): выданное право может заработать, а отозванное — перестать действовать с задержкой до 30 с.
   Права базовых ролей (Viewer/Editor) кэшируются до 60 с. Для чувствительных систем уменьшите TTL.
2. **Роль на команде делегирует доступ администраторам команды.** Кто может добавлять участников команды
   (Admin команды), фактически выдаёт им её роли. Назначайте мощные роли только командам, составом которых управляют админы
   организации.
3. **Grafana Admin не ограничен.** Он может создать роль с серверными правами и назначить её любому пользователю — так задумано.
4. **YAML-роли доверенные.** Файлы `provisioning/access-control/*.yaml` применяются без проверки повышения прав —
   права на запись в каталог provisioning равны правам Grafana Admin. Монтируйте его только для чтения (так в `docker-compose.yml`).
5. **Повторное использование uid источника.** Права из кастомных ролей, выданные на конкретный uid, переживают удаление
   источника; если Admin создаст новый источник с тем же uid, права перейдут на него. Не переиспользуйте uid.
6. **Поиск id по имени.** `/api/datasources/id/:name` отдаёт числовой id любого источника всем Viewer
   (штатная роль `fixed:datasources.id:reader`, как в Enterprise). Данные источника при этом недоступны.
7. **Админ организации может ослабить или удалить роль**, созданную Grafana Admin (но не добавить в неё права сверх своих).
